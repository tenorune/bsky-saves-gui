# v0.6.0 retain-flag — GUI implementation plan

> **Status:** prep / not started. The requirements are settled on both sides
> (`bsky-saves/docs/option-b-retain-flag-gui-requirements.md`, latest commit
> `c04d337`), but the GUI implementation is **blocked on two things shipping
> from `bsky-saves`** — see "Gating dependencies" below. This doc front-loads
> the design so that, once unblocked, implementation is mechanical.
>
> **Scope:** GUI side only. The CLI/daemon side is `bsky-saves`'s requirements
> doc. This plan maps that doc onto concrete `bsky-saves-gui` files and
> sequences the work.

---

## 1. What v0.6.0 adds

`bsky-saves` v0.6.0 introduces **retention + lifecycle flagging**: instead of
the inventory being a whole-result snapshot of the current server state, each
bookmark record carries lifecycle flags, and a user-selected **mode** decides
whether absent / dead-subject entries are dropped or retained.

Four new optional per-entry fields (`§2` of the requirements doc):

| Field | Meaning |
|---|---|
| `last_seen_at` | ISO timestamp of the most recent fetch in which this URI was present. Refreshed every fetch the URI appears in. |
| `removed_detected_at` | Set when a URI present in prior inventory is absent from a *complete* fetch (Class 1 — the user un-saved it). Cleared when the URI reappears. |
| `subject_status` | `"not_found"` / `"blocked"` / `"unknown"`. Absent ⇔ subject post is live. `"not_found"`/`"blocked"` = the post was deleted / author blocked the user (Class 2 — "lost" outside the user's control). `"unknown"` = entry only ever seen via the `listRecords` fallback, which carries no subject state. |
| `subject_status_detected_at` | Set when `subject_status` first becomes non-live. Not set for `"unknown"`. |

Three reconcile **modes**:

- **`sync`** — mirror the server: drop absent-URI entries *and* prune dead-subject entries.
- **`keep-lost`** (default) — drop absent-URI entries (deliberate un-saves), but keep dead-subject entries ("lost" = removed outside the user's control).
- **`keep-all`** — retain everything; absent entries just get `removed_detected_at` stamped.

Four view **filters** (overlapping categories — one entry can be both `lost` and `unsaved`): `synced`, `lost`, `unsaved`, `all`.

## 2. Gating dependencies (why GUI work can't fully land yet)

1. **Golden fixtures.** The requirements doc makes parity between the CLI's
   reconcile (Python) and the GUI's reconcile (TypeScript) a hard CI gate,
   enforced by shared fixtures in `bsky-saves/tests/fixtures/retain/`.
   Implementing the GUI reconcile *before* those fixtures exist means writing
   it with no way to verify it matches the CLI — high divergence risk. The
   reconcile algorithm (Task B) **must wait for the fixtures**.

2. **`bsky-saves` v0.6.0 on PyPI.** `subject_status` is derived in
   `normalise_record` in the core `bsky_saves` package, so both the `/fetch`
   helper path and the in-browser Pyodide path produce it — but only once
   v0.6.0 is the installed/vendored version. End-to-end testing against a
   real backend is blocked until then.

What is **not** blocked: the schema additions (Task A), the mode-persistence
store (Task C), the mode-selection + filter UI scaffolding (Tasks D/E — the
controls can be built and persisted before the reconcile behind them is
live), and designing the CI fixture-fetch plumbing (Task F).

## 3. Tasks

### Task A — Inventory schema: add the four optional fields

**File:** `app/src/reader/inventory-shape.ts` (the `Save` type + `parseSave`).

Add `last_seen_at`, `removed_detected_at`, `subject_status`,
`subject_status_detected_at` as optional fields on `Save`. `parseSave` should
pass them through (type-checked: strings; `subject_status` constrained to the
three literals). All optional — a pre-v0.6.0 inventory simply has none of
them, and the reconcile treats "absent" correctly.

Low risk, no behaviour change. Can land any time; not gated.

### Task B — The reconcile function ⚠ gated on golden fixtures

**File:** `app/src/lib/library-refresh.ts`.

Today `mergeHydratedFields` is `void`-returning, mutates save *objects* in
place, and only field-fills hydration annotations — it never changes the
`saves` *array*. The v0.6.0 reconcile (`§4` of the requirements doc) needs to
*also*:

- run a lifecycle-flag pass on every entry (`last_seen_at`, clear
  `removed_detected_at` on reappearance, the three-case `subject_status`
  reconciliation),
- **drop** absent-URI entries (`keep-lost` / `sync`) or **retain + flag** them
  (`keep-all`),
- **prune** dead-subject entries (`sync` only).

That changes the *record set*, not just fields — so the function's contract
changes. Recommended structure (per `§4.1` of the requirements doc): a new
**`reconcileInventory`** that *wraps* the existing field-fill logic as its
step-3 sub-step and returns a new inventory, rather than an in-place mutation.
Call sites in `startLibraryRefresh` change from `mergeHydratedFields(partial,
prior)` (void) to `partial = reconcileInventory(partial, prior, mode)`.

Note the existing `mergeHydratedFields` JSDoc invariant — *"Never overwrite
fresh data from the new fetch"* — does **not** hold for the lifecycle flags,
which sometimes *clear* (`removed_detected_at` on reappearance,
`subject_status` + `subject_status_detected_at` when a post goes live again).
The new function's docstring must state the field-fill vs. lifecycle-pass
distinction.

The §4 `subject_status` reconciliation has three cases — code them exactly
against the requirements doc, they are subtle:
- **fresh live (no `subject_status`)** → delete `subject_status` *and*
  `subject_status_detected_at`.
- **fresh ∈ {`not_found`, `blocked`}** → set the status; set
  `subject_status_detected_at = now` *only* on a transition (prior had no
  status, or a different one — including the brand-new-URI case and
  `"unknown"` → known); carry prior's timestamp forward if the status is
  unchanged.
- **fresh `== "unknown"`** → **no-op for any existing entry** (never
  overwrites / weakens / clears, never touches `subject_status_detected_at`);
  store `"unknown"` *only* for a brand-new URI, and even then set no
  timestamp. (`"unknown"` is a content-blind `listRecords`-fallback signal —
  it must not erase what a hydrated fetch established.)

**Verification:** every fixture in `bsky-saves/tests/fixtures/retain/` run
through `reconcileInventory`, asserting the result equals the fixture's
`expected_output_inventory`. This is the parity gate — see Task F.

### Task C — Mode-persistence store

**New file:** `app/src/lib/retain-mode.ts`, following the established
preference-store pattern (`asset-toggles.ts`, `operator-proxy-opt-out.ts`,
`install-hint-pref.ts`): a `writable` seeded from IndexedDB, plus
`load*` / `set*` / `clear*` functions. Value: `'sync' | 'keep-lost' |
'keep-all'`, default `'keep-lost'`.

`clear*` must be wired into `Settings.clearAll` *only if* the mode is
considered user data — but it's a per-device preference like the asset
toggles, so it should follow their precedent: **survive Clear data, reset
only via "Reset preferences"** (`clearAllPreferences`). Confirm with the
operator when implementing.

Not gated — can be built before the reconcile consumes it.

### Task D — Mode-selection UI

**File:** `app/src/routes/Settings.svelte` (Backup section, near the asset
toggles). A three-way control bound to the Task C store.

`§5.2` of the requirements doc explicitly delegates labelling to the GUI:
use **descriptive labels**, not the bare `sync` / `keep-lost` / `keep-all`
identifiers — the distinction ("mirror the server" vs. "keep posts lost
outside your control" vs. "keep everything") is not self-evident from the
names. Suggested copy is a UX decision; draft it when implementing.

Can be built + persisted before the reconcile is live (it just writes the
store; nothing reads it yet).

### Task E — Filter control

**Files:** `app/src/lib/library-filters.ts` (predicate logic) +
`app/src/routes/Library.svelte` / `LibraryStatusPanel.svelte` (the control).

Add a `synced` / `lost` / `unsaved` / `all` view filter alongside the
existing query/date filters. Predicates:
- `synced` — no `removed_detected_at`, `subject_status` absent.
- `lost` — `subject_status ∈ {not_found, blocked}`.
- `unsaved` — `removed_detected_at` present.
- `all` — no filter.

Categories overlap by design (an entry can be both `lost` and `unsaved`) —
the control is a single-select view filter, not mutually-exclusive buckets.
Default view filter: `synced` (per `§5.1` — hides the first-run drop impact).

Investigate `library-filters.ts`'s current shape before implementing — the
new dimension should slot into the existing filter store/predicate
composition, not bolt on beside it.

### Task F — CI golden-fixture gate ⚠ gated on fixtures existing

**Files:** `.github/workflows/ci.yml` (or `release.yml`) + a new test file
`app/src/lib/reconcile-fixtures.test.ts`.

The requirements doc leaves fixture *consumption* to us: git submodule vs.
pinned raw-content fetch. **Decision: pinned raw-content fetch** — a
commit-SHA-pinned fetch of the `bsky-saves/tests/fixtures/retain/` files in a
CI step, consistent with how this repo already pins cross-repo dependencies
(`GUI_VERSION` in the wheel, `cdxgen` version in `release.yml`) and avoiding
submodule-checkout weight.

Mechanics:
- A pinned `BSKY_SAVES_FIXTURES_REF` (commit SHA) in the workflow or a small
  config file.
- A CI step that fetches the fixture JSON files from
  `raw.githubusercontent.com/tenorune/bsky-saves/<ref>/tests/fixtures/retain/`.
- `reconcile-fixtures.test.ts` loads each fixture (`input_inventory` +
  `mode` + `expected_output_inventory`), runs it through `reconcileInventory`,
  asserts deep equality.
- Per the requirements doc: a coordinated release does not bump the wheel's
  `gui_version` until both repos are green on these fixtures.

## 4. Sequencing

```
Task A (schema) ─────────────────┐
                                 ├──► Task B (reconcile) ──► Task F (CI gate)
[golden fixtures published] ─────┘         │
                                           ▼
Task C (mode store) ──────────────► Task D (mode UI) wires to B
Task E (filter) ──────────────────────────┘ (reads B's flags)
```

- **A** can land immediately (own commit / first PR).
- **C, D, E** can be built in parallel with each other, before **B** — the UI
  controls persist state and render filters; they just have nothing
  behaviourally behind them until **B** lands. (Acceptable: a mode selector
  that's persisted but inert, a filter that matches nothing until flags
  exist.)
- **B** is the gated centrepiece — starts when the golden fixtures are
  published and pinnable.
- **F** lands with or immediately after **B** (it's how **B** is verified).

A reasonable PR breakdown: PR1 = Task A. PR2 = Tasks C+D+E (UI scaffold,
inert). PR3 = Task B + Task F together (the reconcile and its parity gate
are meaningless apart).

## 5. Key decisions already made

- **Reconcile structure:** new `reconcileInventory` wrapping `mergeHydratedFields`'s field-fill as a sub-step; returns a new inventory rather than mutating in place. (`§4.1`)
- **Fixture consumption:** commit-SHA-pinned raw-content fetch, not a submodule.
- **Partial-fetch guard:** already satisfied by both GUI fetch backends and now **documented as a code invariant** — see the "COMPLETE-FETCH INVARIANT" comment in `library-refresh.ts` and the "ALL-OR-NOTHING PAGINATION" comment in `fetch-hydrator.ts`. No new guard code needed; the comments exist so a future refactor doesn't silently break it.
- **Default mode:** `keep-lost`. **Default view filter:** `synced`.
